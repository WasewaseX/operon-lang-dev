Root cause (src/value.rs): `position()` fell back to a FULL linear deep_eq
scan on every memo miss (needed for exactness because deep_eq(Int 2,
Float 2.0) is true and 0.0 == -0.0 — repr hashing cannot cross tags), and
`del()` rebuilt the whole memo (O(N) hash inserts per delete). The memo
itself probed a `HashMap<(u8, u64), usize>` — one SipHash over the key's
canonical bytes plus a second SipHash over the tuple inside HashMap.

## 2. The rework (semantics-preserving, src/value.rs only)

1. **Single-hash open-addressed memo**: slots `(u64 hash, u32 position)`,
   linear probing, load <= 1/2, rehash-from-items on growth (amortized O(1)),
   tombstones on delete. One hash per lookup, no tuple re-hash, no std
   HashMap. Hash: dependency-free FNV-1a (str/bytes/canonical-float bytes)
   or a Fibonacci mix (int bits) — the memo is pure accelerator state, never
   observable, deep_eq-verified on every hit (the same license the SipHash
   design relied on).
2. **Miss-trust, the O(1) absence proof**: within a scalar class,
   deep_eq-equal values always hash equal (Str: same bytes; Int: bit
   bijection via `as`; Bool/Null: constants; Bytes: same bytes) and every
   scalar item's hash is stored — an empty probe PROVES absence, no
   fallback scan. Soundness hole = exactly the Int<->Float cross class;
   the store counts numeric (Int/Float) keys: zero of them -> numeric
   lookups trivially absent; any -> exact full scan (numeric-keyed maps are
   not the hot workload, loglens/csvstat evidence). u64 collisions share a
   slot -> deep_eq verify fails -> exact scan (2^-64, harmless).
3. **del() without rebuild**: one O(capacity) walk shifts stored positions
   past the removed slot; the removed key's slot is tombstoned; rehash when
   tombstones exceed live entries. Batch del: quadratic -> linear.
4. W029 bytes keys now hash by CONTENT (were length-tagged); sec-r5
   non-scalar bounded scan unchanged; insertion-order contract unchanged
   (items Vec untouched; every observable order identical).

Exactness contract: memo hits deep_eq-verified; exact full scan remains the
fallback for every class the table cannot prove. Scalar-key behavior
bit-for-bit identical (proven below).

## 5. Findings filed (all pre-existing, zero prior corpus exposure)

The pin's first draft exposed three oracle gaps — the differential net
working as designed. All are bootstrap/oracle.py (OUTSIDE the P1 lock;
compat lane / owner), so the pin covers only the oracle-agreeable forms
until they are fixed:

1. **Bool/Int map keys collapse in the oracle's write path** (oracle.py
   `idx_assign`, ~line 3946): the rust engine keeps `true` and `1` distinct
   (deep_eq has no Bool/Int cross arm — two slots); the oracle's write path
   keys natively (Python `True == 1` collapse) while its READ path uses
   deep_eq — self-inconsistent.
2. **Null map keys are unreachable in the oracle**: null is not in the
   write path's accepted scalar tuple, so the key is stored as
   `v_display(iv)` (display text); the oracle's own deep_eq read path can
   never find it again. Rust stores Null as Null and finds it.
3. **Container (list/map) keys**: already documented IN oracle.py
   ("fall back to display text, pre-existing divergence, filed for a future
   session") — re-confirmed by the pin's first draft.
