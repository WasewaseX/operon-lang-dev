# P5/P6 survey — strings & numeric data structures (2026-10-04, builder-A)

Survey phase of the S34-approved P5 (Strings) and P6 (Numeric data structures)
rows, verdict bundle S34 2026-10-04 (both APPROVED survey-then-fix). This
document is the survey deliverable: measurements + design-space notes for the
fix phases, **zero production-code delta**. Base: main `54197ef` (v2.8.0,
post W-L1). Agent: builder-A (VM/runtime lane).

## Method

- In-process timing: `operon bench <f.op> --iters 12`, min across 5 fresh
  invocations (CV of invocation-mins reported where relevant). Subprocess
  wall-clock is UNUSABLE below ~5 ms of program work on this box: process
  startup (~1.5 ms) contaminates small fixtures — an earlier scaling run
  measured slope 0.64 (sub-linear, wrong) purely from startup dilution;
  the in-process protocol below is the honest one.
- Memory: child peak RSS (`getrusage(RUSAGE_CHILDREN)`) deltas, with the
  per-element factor taken from the 1M→4M SLOPE, not absolute deltas —
  the interpreter's ~15 MB baseline heap absorbs the first ~10 MB of new
  allocations, so absolute deltas under-read; the slope does not lie.
- Allocation attribution is code-precise (line numbers below) + black-box
  scaling; no valgrind/DHAT available in this environment. Exact per-op
  alloc counters would need an env-gated instrument (fix-phase option).
- Fixtures are session-local (this survey commits documentation only);
  the commit candidates are listed at the end.

## P5 — Strings

Charter (roadmap): "Investigate repeated concatenation and allocation
behavior, especially the variance shown by strconcat10k."

### 1. The named workload does not exist

No `strconcat10k` fixture ships in the repo (roadmap name predates the
current suite). Recreated as the scaling family below so the charter's
named experiment exists: `cat_N.op` = `let s = "" ; for i in range(N)
{ s = s + "x" }` at N ∈ {1k, 2k, 4k, 8k, 16k}, plus shape variants
(catconv = `+ str(i % 10)`, joinbuild = push-then-`"".join`).

### 2. Repeated concatenation is quadratic-total — CONFIRMED by measurement

| N | min (ms) | ns/op | t(2N)/t(N) |
|---:|---:|---:|---:|
| 1,000 | 0.415 | 415 | — |
| 2,000 | 0.870 | 435 | 2.10 |
| 4,000 | 1.827 | 457 | 2.10 |
| 8,000 | 4.061 | 508 | 2.22 |
| 16,000 | 9.576 | 599 | 2.36 |

Per-op cost grows linearly with |s| (415 → 599 ns as the string grows to
16 KB) and the doubling ratio drifts above 2 — the quadratic-total
signature. Cause (code-precise): `Value::Str + Value::Str` is
`format!("{}{}", a, b)` — interp.rs:3968 — a fresh String allocation
copying BOTH operands on every op. For the accumulation shape that is
O(|s|) bytes copied per op, O(N²) total.

### 3. Variance: engine-side string timing is stable

Across 5 invocations × 12 iters, CV of invocation-mins: 0.3–0.9% on every
string fixture (cat family, m_strcat, strings, split, interp). The
roadmap's variance concern does NOT reproduce as engine variance on this
sandbox; it reproduces only as subprocess startup/scheduler noise (CV up
to ~10% wall-clock). Recommendation: the fix phase should quote in-process
mins, never subprocess wall-clock, for sub-10 ms workloads.

### 4. Per-op string costs at 10k scale (fresh, in-process)

| op | ns/op | notes |
|---|---:|---|
| concat `s + "x"` | ~540 @10k | N-dependent (415@1k → 599@16k), see table |
| `str(i % 10)` conversion | +~140 | interp.rs:7264, `display()` String alloc |
| split 9-field line | ~1,024 | interp.rs:11515: Vec + Rc + RefCell + 9 piece `to_string` allocs + charge walk (~12 allocs) |
| 4-hole interpolation | ~822 | interp.rs:3582: `String::new()` + per-expr `display()` alloc + push_str |
| join 10k pieces (join phase) | ~280/piece | interp.rs:11747: `Vec<String>` collect (per-piece `display()` alloc) THEN `parts.join` |

### 5. Builder shape vs accumulation (measured)

`joinbuild_10000` (10k pushes + `"".join`) = **3.94 ms** vs the equivalent
accumulation ≈ 5.4 ms at N=10k (interpolated from the table). The builder
shape wins, but join carries its own churn — the `Vec<String>` collect
materializes every piece (10k allocs) before the single join copy. A
streaming join (iterate + push_str, skip the Vec<String>) is a cheap
intermediate win; the real endgame is the BENCH.md item-6 idea: a
builder fast path for the `s = s + x` accumulation shape.

Fix-phase upside (honest range): accumulation → true builder ≈ quadratic
→ linear. At 10k: ~5.4 ms → ~0.4–1.2 ms (push loop + one final copy) =
**4–13x on the accumulation shape**; loglens-class workloads with heavy
string assembly inherit a slice of that.

### 6. Drift notes against BENCH.md's recorded rows (e757b4d era)

- `m_strcat`: fresh 9.39 ms vs recorded 10.0 ms — flat (no regression;
  the recorded ns/op column uses the harness's own op calibration, which
  differs from fixture-N math; compare absolute ms only).
- `strings` workload: fresh **4.73 ms** vs recorded 26.0 ms — 5.5x faster
  than the recorded row (loop-path + interp improvements since e757b4d;
  the recorded row is stale).

## P6 — Numeric data structures

Charter (roadmap): "Add an efficient typed numeric-array representation
suitable for simulation and numeric programs. Lists/maps must not become
the mandatory representation for high-volume numerical state."

### 1. Representation facts (measured)

`Value` is a 32-byte tagged enum (the `Str(String)` variant's 24-byte
payload drives the layout). Numeric lists are `Vec<Value>`: every i64
costs 32 bytes + tag-check per access.

- RSS slope 1M → 4M boxed ints: **31.4 B/elem** — confirms the 32-byte
  layout. A typed i64 array needs 8 B/elem → **4.0x memory factor**.
- 1M-float list: consistent (300k → +10.2 MB peak incl. slack).

### 2. `range()` is EAGER — the headline finding

interp.rs:7240: `range(a, b, step)` materializes a full `Vec<Value>` of
boxed ints on EVERY call (10M-element ceiling), before iteration starts.

- Measured build cost: **11.4 ns/elem** (N=1M: 11.4 ms; N=200k: 1.96 ms;
  linear in N).
- N=1M: 33.5 MB retained for the loop's integer sequence.
- Consequence: the most common loop shape in the language —
  `for i in range(N)` — pays a full boxed-Vec materialization up front.
  Amortized ~10 ns/iter at 1M scale: visible, not dominant vs the
  ~264 ns/iter loop machinery, but pure overhead a lazy or typed range
  eliminates. It also sets the memory high-water: `range(4_000_000)`'
s sequence costs ~128 MB before the body runs.

### 4. Design-space notes for the fix phase

1. **Typed IntArray/FloatArray variant** (the charter's ask): e.g.
   `Value::IntArray(Arc<Vec<i64>>)` (+FloatArray). Transparent bridging
   rules: element read materializes `Value::Int`; element write
   transitions the representation (or the rep is opt-in via a builtin
   `int_array(n|xs)`); `len`/index/iterate/join/display/repr must be
   identical to the list shape (differential contract: byte-identical
   stdout + exit across VM / tree-walk / oracle — semantics unchanged
   means the Python oracle needs no behavioral change).
2. **Lazy range** alternative: no new Value variant; a Range value that
   iterates without materializing (materialize only when indexed/passed
   to list-expecting surfaces). Smallest delta, kills the eager-Vec
   overhead; does NOT help non-range numeric state (the charter's
   simulation concern).
3. **Streaming join** (P5/P6 boundary): iterate + push_str, skip the
   `Vec<String>` intermediate at interp.rs:11747.
4. Benefit surfaces: range loops (everywhere), numeric list build/index
   (loglens aggregation ≈ 255 ms map-counting class — note P1's MapStore
   work lands first and shifts that number), grn level vectors,
   csvstat numeric columns.
5. **Sequencing recommendation: P6 fix AFTER P1 lands.** Both touch
   value.rs / the container layer; landing P6 first would hand P1 a
   rebase. The lazy-range vs typed-array choice is the fix phase's first
   decision — measure both against the same fixtures before choosing.
